## 1. BrickUIKit 包

### 1.1 位置与接入

**包位置**：`/Users/suipu/Dev/Shadeling/app/packages/BrickUIKit/`

理由：设计系统所有权归底座，积木是下游消费方；避免"底座反向依赖发布区仓库"的怪味。

```
Shadeling/app/
├── Package.swift                    # 加 .package(path: "packages/BrickUIKit")
├── packages/
│   └── BrickUIKit/
│       ├── Package.swift            # tools 6.0 / platforms macOS 14 / target BrickUIKit
│       └── Sources/BrickUIKit/
│           ├── Tokens.swift         # 令牌层（从 Design.swift 原样搬入）
│           ├── Components.swift     # 卡片/排版/输入/按钮/动效

│           └── BrickOverlays.swift  # 弹层 + 状态条
└── Sources/ShadelingApp/
    └── Design.swift                 # 瘦身：只留 NavSection 等底座专属内容
```

**依赖声明**：

| 消费方 | 声明 |
|---|---|
| 底座 `Shadeling/app/Package.swift` | `.package(path: "packages/BrickUIKit")` + target 依赖 `"BrickUIKit"` |
| 产品 `brick-vault/products/<id>/source/Package.swift` | `.package(path: "../../../../Shadeling/app/packages/BrickUIKit")` + target 依赖 `"BrickUIKit"` |

路径核算：`~/Dev/brick-vault/products/vault/source` → 上 4 级 = `~/Dev` → 拼 `Shadeling/app/packages/BrickUIKit`。

**出包前置检查**：`package_app.sh` 新增步骤 0——依赖路径不存在则 abort 并提示，避免"本地能编、换机器报错"。

### 1.3 窗口契约（硬约束）

| 项 | 统一值 | 现状差距 |
|---|---|---|
| windowStyle | `.hiddenTitleBar` | wechat-mp 用系统标题栏 → 需改 |
| defaultSize | **980 × 680** | wechat-mp 无 defaultSize → 需补 |
| 最小尺寸 | **760 × 520** | wechat-mp 现为 1120 × 720 → 需改 |
| WindowGroup 数量 | 1，且禁用 Cmd+N | 两者均需统一（vault 现未禁用） |
| 关最后一个窗口 | **即退出进程** | 两者均未实现 → 必须补 |
| 窗口尺寸/位置记忆 | 交给系统 | 不自定义 |

**`BrickScene` 参考实现**：

```swift
public struct BrickScene<Content: View>: Scene {
    let title: String
    @ViewBuilder let content: () -> Content

    public var body: some Scene {
        WindowGroup(title) {
            content()
                .frame(minWidth: 760, minHeight: 520)
                .background(BrickLifecycleView())   // 关窗即退 + 激活
        }
        .windowStyle(.hiddenTitleBar)
        .defaultSize(width: 980, height: 680)
        .commands { CommandGroup(replacing: .newItem) {} }
    }
}
```

**`BrickLifecycleView`**（不可见辅助视图）职责：
1. `onAppear` → `NSApp.activate(ignoringOtherApps: true)`（被 `openApplication` 拉起时确保置前）
2. 监听 `NSWindow.willCloseNotification` → 若无可见窗口则 `NSApp.terminate(nil)`

> 第 2 条是单实例方案的必要配套：积木不退出，底座就无法感知、点击入口会"没反应"。

**积木侧写法（迁移后）**：

```swift
@main
struct VaultApp: App {
    var body: some Scene {
        BrickScene(title: "本地资产中枢") { ContentView() }
    }
}
```

## 2. 单实例 + 幂等激活（底座侧改造）

### 2.1 现状

`AppModel.launchProductBrick`（`AppModel.swift` L2752）硬编码：

```swift
config.createsNewApplicationInstance = true    // ← 多实例根源
```

每点一次入口即开一个新进程（实测 wechat-mp 已跑 3 个实例，无人回收）。

### 2.2 改造方案

1. 底座新增 `runningBricks: [String: NSRunningApplication]`（key = `manifest.brickID`）；
2. `openProductBrick` 前置判定：
   - **命中运行中实例** → `app.activate()` 带到前台，**不重启、不重发令牌**（幂等）；
   - **未命中** → `createsNewApplicationInstance = false` 打开 → 注入桥令牌 → 登记 pid；
3. 沿用既有 `didTerminateApplicationNotification` 观察者，进程退出时移除登记；
4. 令牌策略：复用实例时沿用旧令牌（TTL 43200s）；超过 TTL 的 refresh 端点列为后续项。

### 2.3 验收标准

| 项 | 预期 |
|---|---|
| 连点同一积木入口 5 次 | 仅 1 个进程、1 个窗口，窗口置前 |
| 关闭窗口后 | `pgrep -f "Vault.app"` 为空 |
| 关窗后再点入口 | 正常重新拉起并注入新令牌 |
| 积木崩溃/强退后 | 登记被清理，点击可重新拉起 |

### Phase 4 — 脚手架：一条命令生成完整产品积木

**目标**：把 `scripts/new_brick.py` 从"生成声明式积木骨架"升级为"生成完整产品积木工程"，让新积木起手从"抄一份 vault、逐处改"变成"一条命令 + 直接写业务"。

**现状差距**：`new_brick.py`（约 10KB）产出的是 `bricks/<id>/brick.json` 声明式骨架，与 V2 产品积木形态（`products/<id>/source/` + `manifest.json` + `releases/`）完全不匹配，产不出可编译的产品工程。

**升级后用法**：

```bash
python3 scripts/new_brick.py product --id my-brick --title "我的积木" --platform 14.0
```

**生成内容**：

```
products/<id>/
├── manifest.json                 # 身份字段预填，download_url 按发布规范拼好
├── source/
│   ├── Package.swift             # 已含 BrickUIKit 相对路径依赖 + target 依赖
│   ├── Info.plist                # bundle id = com.shadeling.brick.<id>
│   ├── package_app.sh            # 复制自 vault，替换 PRODUCT/BUNDLE_NAME/EXECUTABLE + 依赖前置检查
│   ├── icon.png                  # 占位图标
│   └── Sources/<Target>/
│       ├── <Target>App.swift     # @main + BrickScene 骨架
│       └── ContentView.swift     # 玻璃壳 + 空态视图
└── releases/                     # 空目录，出包时生成
```

**生成后自检**：自动跑一次 `verify_products.py`，**生成即通过闸门**，杜绝"新建的积木天生不合规"。

**闸门扩展（Phase 3 追加两条）**：

4. `products/<id>/source/Package.swift` 必须含 BrickUIKit 依赖（脚手架产物天然满足）；
5. 脚手架生成的 manifest 必须通过 `verify_products.py` 全量校验。

### 三层分工（模板能解决什么、不能解决什么）

| 层 | 载体 | 解决什么 | 不解决什么 |
|---|---|---|---|
| 脚手架 | `new_brick.py product` | 起手速度：从 0 到可编译可运行 | 业务逻辑 |
| 模板 | BrickUIKit 三层契约 | 一致性：窗口/按钮/弹层/配色不漂移 | 业务逻辑 |
| 闸门 | `verify_products.py` | 质量不退化：违规在出包期被拦 | 业务逻辑 |

> **重要认知**：三者都不加速业务实现。积木的主要工作量在接口对接、数据模型、状态机、领域视图，这部分时间不因模板而减少。模板体系的真实收益是"固定成本归零 + 返工消失"，而非"业务开发变快"。
